# Сверка банковских поступлений

Небольшой сервис для детерминированной сверки банковских поступлений со счетами. Он показывает полностью, частично и ещё не оплаченные счета, оставляет неоднозначные поступления нераспределёнными и формирует Excel-отчёт для аудита.

## Запуск

Требуется Docker с Docker Compose.

```bash
make up
```

Docker-образ устанавливает закреплённую версию `uv` из PyPI и не требует доступа к GHCR.

После сборки интерфейс доступен по адресу [http://localhost:8000](http://localhost:8000). Остановка:

```bash
make down
```

Для локальной разработки нужен Python 3.12+ и `uv`:

```bash
make install
make check
```

Полезные команды:

```bash
make test       # pytest и coverage
make lint       # ruff
make typecheck  # mypy --strict
make format     # ruff format
make logs       # логи контейнера
```

## Использование

1. Откройте главную страницу.
2. Выберите банковскую выписку `.csv` и реестр счетов `.xlsx`.
3. Нажмите «Запустить сверку».
4. Проверьте итоговые суммы, предупреждения и нераспределённые поступления.
5. Скачайте Excel-отчёт.

Сформированные отчёты хранятся только в памяти процесса, не более 15 минут. История запусков в MVP отсутствует.

## Архитектура

```text
FastAPI / Jinja2
        |
        v
Application service
        |
        v
Domain matching + validation
        ^
        |
      Ports
        ^
        |
CSV / XLSX / Excel adapters
```

Domain и application layer не импортируют FastAPI, Jinja2, openpyxl или детали файлов. Источники реализуют бизнес-порты `PaymentSource` и `InvoiceSource`, а отчёт — `ReportExporter`. Matching состоит из небольших упорядоченных правил и не использует fuzzy/LLM matching.

Порядок правил:

1. Явная ссылка на один счёт.
2. Явные ссылки на несколько счетов.
3. Единственный неоплаченный счёт с тем же ИНН и точной суммой.
4. Платёж остаётся нераспределённым.

## Какие допущения я сделал

- Явная ссылка на invoice имеет приоритет над ИНН плательщика. Несовпадение ИНН отображается предупреждением.
- `ИНН + точная сумма` используется только для единственного полностью неоплаченного кандидата.
- Неоднозначный кандидат не выбирается автоматически.
- Переплата распределяется только в пределах суммы счёта, остаток остаётся unallocated.
- Multi-invoice платёж распределяется, только если существуют все явно перечисленные счета и денег достаточно для их закрытия. Недостаточная сумма не делится по произвольному порядку.
- Полный fingerprint операции включает дату, номер документа, направление, сумму, контрагента, ИНН и назначение. Только точный повтор исключается как duplicate.
- Банковские контрольные суммы валидируют рассчитанные после дедупликации обороты. Нарушение контрольного баланса останавливает обработку.
- Расходы не участвуют в matching, но участвуют в проверке банковского баланса.
- Отчёты доступны по случайному идентификатору и автоматически истекают; это не постоянное хранилище.

## Где ИИ ошибался и как я это заметил

- При первой настройке `uv` ИИ позволил автоматически выбрать установленный Anaconda Python 3.12.4. `pytest` завершался с `exit 139` ещё до сбора тестов. Проверка интерпретаторов показала причину, после чего окружение было пересоздано на uv-managed CPython 3.12.14.
- Первая версия XLSX-adapter обрабатывала ошибки `openpyxl`, но не перехватывала `zipfile.BadZipFile`. Негативный тест с повреждённым `.xlsx` показал утечку инфраструктурного исключения вместо понятной ошибки; обработка была расширена.
- В первой версии теста Excel-экспорта проверялась неверная ячейка Summary. Тест упал на значении распределённой суммы вместо нераспределённой; расположение строк было перепроверено, а assertion исправлен на фактическую строку метрики.
- Первая визуальная проверка Excel показала, что широкие таблицы разбиваются на две горизонтальные страницы и обрезают названия компаний. Экспорт был дополнен вычислением ширины колонок, переносом текста и печатью в одну страницу по ширине.

## Что бы я доделал, будь у меня ещё день

- Добавил ручное разрешение неоднозначных платежей с сохранением автора и причины решения.
- Добавил постоянную историю запусков, audit log и повторное скачивание отчётов.
- Вынес matching policies и форматы банковских адаптеров в конфигурацию.
- Добавил аутентификацию/RBAC и ограничения доступа к финансовым данным.
- Добавил мониторинг ошибок импорта, времени обработки и нарушений invariants.
- Подготовил adapters для 1С, CRM и банковского API без изменения domain core.
